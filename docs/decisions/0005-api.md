# 0005 — The API: one JSON answer, and the free tier's budget as the thing to protect

**Status:** accepted · 2026-10-20

## Context
P6 puts the answer pipeline behind HTTP for a public demo (P7: a Hugging Face Space, one
small machine, one process). Two facts shape it. Every answer must be verified before any
of it is shown (ADR 0004). And the scarce resource is not CPU but the model's free tier:
Groq allows 200,000 tokens a day per model, shared by every visitor; one evaluation run
spent a third of a model's day, and three in a row ran one dry.

## Decisions

**Routes.** `POST /chat`, `GET /section/{id}`, `GET /map/{id}`, `POST /feedback`,
`GET /health`. Section ids are anchored patterns (`^(IPC|BNS):\d{1,3}[A-Z]{0,3}$`) and then
looked up in the bundle, so a path never names anything but a section.

**`/chat` returns one JSON body, not a token stream (the plan said SSE).** Streaming would
show text before the checker has passed its section numbers. Answers take about a second
(p95 1.3 s in ADR 0004), so the stream would buy little.

**An explicit `offence_date` overrides the dates in the text** (ADR 0003 required it).
It decides the route for retrieval as well as for the answer: the pipeline takes the
facts the service already understood instead of re-reading the question. The first
version re-read them, so the model could be told "the IPC applies" while shown only BNS
sections. Code review caught it; the stub retriever in the tests could not. A question
that names the other code ("BNS equivalent of IPC 379") is a map lookup whatever the date.

**Budget, in layers.**
| guard | limit | protects against |
|---|---|---|
| per client, all routes | 5 requests a minute | bursts |
| per client, `/chat` | 50 questions a day | one visitor spending everyone's day |
| all clients, model calls | 400 a day | the shared token budget (~570 answers over two models) |
| in flight | 4 answers at once, own thread pool | slow model calls holding every thread |
| answer cache | 512 answers, 24 h, answers and clarifications only | paying twice for one question |

A refused request is told why and when to return (`Retry-After`). A cached answer costs
no model call and is served even when the day's budget is spent.

**Client identity.** The limit keys on the address the trusted proxy appended to
`X-Forwarded-For` (`LEXBRIDGE_PROXY_HOPS` entries from the right), never on one left of
it, which the client wrote. Not uvicorn's `--proxy-headers`: without it every visitor shares
the proxy's address; trusting every hop with it takes an address the client chose. IPv6 is
limited per /64. Idle clients are forgotten once a window; past 10,000 tracked clients new
ones wait rather than grow memory.

**Errors** have one shape, `{"error": {"code", "message"}}`, with field-level detail for
invalid requests. No exception text reaches a client (a provider outage is 503
`LLM_UNAVAILABLE`, a rejected request 502 `LLM_ERROR`, the day's budget 503
`DAILY_LIMIT`, anything else 500 `INTERNAL`). Unexpected errors are logged by type and
frames only, from a middleware: starlette re-raises after an `Exception` handler, and the
server then logged the full message, which can quote the question.

**Traces without personal data.** Each answer is logged to SQLite with an HMAC-SHA256 of
the question under a server key (repeats stay visible; a leaked file cannot be checked
against guessed questions, as a bare hash could), plus status, code, citations, latency
and cache use. The newest 100,000 rows are kept. A failed trace write does not fail a
paid-for answer.

**Bodies over 8 KB are refused before they are read; the interactive docs are off.**

**Tests call the app through `httpx.ASGITransport`,** not starlette's `TestClient`, which
from starlette 1.x needs the separate `httpx2` package.

## Consequences
- P7 runs `uvicorn --factory lexbridge.api.main:build` with `LEXBRIDGE_PROXY_HOPS=1`,
  `LEXBRIDGE_TRACE_KEY` set as a secret, and without `--proxy-headers`. The hop count must
  be confirmed on the Space by echoing what it receives.
- The limits are in-process: a restart forgets them, and a second replica would double
  them. Both are acceptable for one demo process.
- The global cap means a busy day ends in `DAILY_LIMIT` for new questions rather than in
  provider 429s; cached answers keep working.

## Smoke test (real bundle, bge-m3, Groq, through uvicorn)
- "cheated of money in August 2024" → BNS 318, the date assumption stated first.
- The same without a date → asks when; "capital of Australia" → declined; an unknown
  section → 404; a repeat → served from the cache; the per-minute limit → 429.
- "stolen on 5 August 2024" with `offence_date` 2024-03-05 → routed to the IPC, and all
  four sources retrieved were IPC sections.
- Two answers were grounded but not the best section: "cheated ... March 2024" cited
  IPC 418 (cheating a person whose interest one must protect) rather than 415/420, and
  "phone stolen" cited IPC 410 (stolen property) rather than 378/379. That is the
  retrieval limit ADR 0003 measured on lay questions (hit@5 68%), not a checker failure.
  The override answer's prose also repeated the question's own date; the opening line
  states the date that decided.
